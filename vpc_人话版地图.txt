核心比喻：你的 VPC = 一栋楼
─────────────────────────
把整个 AWS VPC 想象成「一栋公寓楼」，你会发现每个技术名词
都能对应到生活里的一个东西。


┌──────────────────────── 术语对照总表 ────────────────────────┐
│                                                              │
│   技术名词            楼里的比喻          它到底管什么         │
│   ───────────────    ──────────────     ──────────────────  │
│   VPC                 整栋楼             你专属的隔离网络     │
│   Subnet（子网）      楼里的一层         把楼分成几块区域     │
│   ENI（网卡）         房间的电话分机     机器的网络接口       │
│   私有IP 10.0.x.x     房间内部分机号     楼内互相找人用       │
│   IGW                 楼的【大门】       楼通不通城市马路     │
│   公网IP / EIP        对外【门牌号】     城市邮政认得的地址   │
│   NAT Gateway         门口【传达室】     只出不进的单向代理   │
│   RouteTable（路由）  楼里的【路标】     "去X地方往这走"      │
│   SecurityGroup       门口的【保安】     谁能进/出的名单      │
│   Nitro 芯片          楼的【物业总控】   底层真正执行所有规则 │
│                                                              │
└──────────────────────────────────────────────────────────────┘

 场景一：楼内串门（VPC 内部通信）—— 不需要大门，不需要门牌号
═══════════════════════════════════════════════════════════════════════════

    ┌─────────────────── VPC 这栋楼 (10.0.0.0/16) ───────────────────┐
    │                                                                │
    │   ┌──────── 一层 subnet ────────┐   ┌──── 二层 subnet ────┐    │
    │   │                             │   │                     │    │
    │   │   [厕所]                    │   │    [厨房]           │    │
    │   │   RDS 数据库                │   │    某个服务          │    │
    │   │   分机号 10.0.1.20          │   │    分机号 10.0.2.30  │    │
    │   │                             │   │                     │    │
    │   └──────────────┬──────────────┘   └──────────┬──────────┘    │
    │                  │                             │               │
    │                  └──────── 楼内走廊 ────────────┘               │
    │              路标(RouteTable): "10.0.0.0/16 → local"           │
    │              意思:目标在楼内,直接走廊送过去,不用出门            │
    │                                                                │
    └────────────────────────────────────────────────────────────────┘

    厨房要找厕所 → 拨内部分机号 10.0.1.20 → 走廊直达。
    全程不需要大门(IGW)、不需要门牌号(公网IP)。这就是 "local" 路由。

 场景二：厕所想被城市快递找到（外网主动访问你的机器）
 ★ 必须四样齐活,缺一不可 ★
═══════════════════════════════════════════════════════════════════════════

              城市马路（公共互联网）
                     │
                     │  快递员送包裹来了
                     ▼
        ┌────────────────────────────┐
        │  ① 大门 IGW                 │  ← 楼得先通马路
        │     没装 IGW = 封闭院子      │     igw.attachToVpc(vpc)
        │     快递连楼都进不来 ❌      │
        └─────────────┬──────────────┘
                      │ 进楼了,但送去哪个房间?
                      ▼
        ┌────────────────────────────┐
        │  ② 门牌号 公网IP/EIP         │  ← 房间得对外有地址
        │     厕所没门牌号 = 找不到 ❌ │     new ElasticIP()
        │     (RDS 默认就没有!)        │
        └─────────────┬──────────────┘
                      │ 找到房间了
                      ▼
        ┌────────────────────────────┐
        │  ③ 路标 RouteTable           │  ← 得知道怎么走回大门
        │     0.0.0.0/0 → igw-xxx      │     egressRT.addRoute(...)
        │     没路标 = 迷路 ❌          │
        └─────────────┬──────────────┘
                      │ 路认得
                      ▼
        ┌────────────────────────────┐
        │  ④ 保安 SecurityGroup        │  ← 最后一关:放不放行
        │     inboundRules 默认空 = 全拒│    sg.allowInbound(
        │     没放行你的IP+端口 ❌      │      "tcp",5432,"你的IP/32")
        │     → Nitro 执行 drop(packet) │
        └─────────────┬──────────────┘
                      │ 四关全过!
                      ▼
              ✅ 包裹送达厕所 (RDS 收到连接)


  ★★ 你之前 psql 被拒,就是卡在 ② 或 ④ ★★
     ② RDS 没公网门牌号(Publicly Accessible = No) → 城市根本找不到它
     ④ 保安没放行你的IP → Nitro 芯片静默 drop → 你的终端傻等 → timed out

 场景三:厕所想自己出门买东西(私网机器主动访问外网)
 —— 用传达室 NAT,而不是自己弄门牌号
═══════════════════════════════════════════════════════════════════════════

    [厕所] RDS 10.0.1.20              城市马路(互联网)
       │  "我要去外面下载更新"              ▲
       │  但我没门牌号,直接出门回不来        │
       ▼                                    │
    ┌────────────────────┐                  │
    │  路标: 0.0.0.0/0    │                  │
    │       → nat-xxx     │  "出门先去传达室" │
    └─────────┬──────────┘                  │
              ▼                              │
    ┌────────────────────────────┐          │
    │  传达室 NAT Gateway          │          │
    │  它有门牌号(EIP 54.200.1.1)  │          │
    │                             │          │
    │  出门时:把寄件人地址改成      │          │
    │  自己的门牌号,并记在小本本上  │──────────┘
    │  (connectionTable)          │   借用大门 IGW 出去
    │                             │
    │  回信时:查小本本,还原成       │
    │  厕所的分机号 10.0.1.20       │
    └─────────────────────────────┘

  关键区别:
    ┌──────────┬─────────────────────┬───────────────────────┐
    │          │  IGW (大门)          │  NAT (传达室)          │
    ├──────────┼─────────────────────┼───────────────────────┤
    │ 方向     │  双向(进+出)         │  单向(只出,别人进不来) │
    │ 谁用     │  有公网IP的房间       │  没公网IP的房间借它出门 │
    │ 安全性   │  暴露                │  隐蔽(外面不知你存在)  │
    │ 典型用途 │  公开网站            │  数据库偷偷连外部API   │
    └──────────┴─────────────────────┴───────────────────────┘

  注意:NAT 自己也没有出网能力! 它只是改地址,然后把包踢回路由系统,
       最终还是要经过【大门 IGW】才能真正出去。
       (代码里 NAT.handleOutbound 只 return,没 sendToInternet)

 谁在幕后执行这一切? —— 物业总控 Nitro 芯片
═══════════════════════════════════════════════════════════════════════════

    你在 AWS 控制台点点点(装大门、发门牌号、写路标、设保安名单),
    这些都只是「往楼的登记册上写规则」。

    而每一个快递(数据包)真正到达时,决定它「放行还是扔掉」的,
    是楼里的【物业总控 = Nitro 芯片】,它在每台物理机上实时执行:

        NitroForwardingEngine.forward(packet, eni) {
           1. 这包属于哪栋楼(哪个VPC)?      → 认标签
           2. 查这栋楼的路标(RouteTable)     → 往哪送
           3. 查这栋楼的保安(SecurityGroup)  → 放不放行
           4. drop(扔掉) 或 deliver(送达)
        }

    ★ 多栋楼(多个客户的VPC)其实共用同一片物理地基(物理服务器/网卡),
      物业总控靠给每个包打标签,保证张三家的快递绝不会送错到李四家。
      → 这就是"看着像独占,实际共享物理"的真相。

 一图记住全部
═══════════════════════════════════════════════════════════════════════════

        私网机器"隐身"  =  它根本没对外门牌号(不是藏起来了)
        IGW            =  楼的大门(通不通马路)
        公网IP/EIP     =  对外门牌号(城市认得的地址)
        NAT            =  传达室(只出不进的代理)
        RouteTable     =  楼里的路标
        SecurityGroup  =  门口保安
        Nitro 芯片     =  物业总控(真正逐包执行规则的硬件)

        想被外界访问 = 大门(IGW) + 门牌号(公网IP) + 路标(路由) + 保安放行(SG)
        想偷偷出门   = 走传达室(NAT),NAT 再借大门(IGW)出去
        楼内串门     = 走走廊(local 路由),啥都不需要

 补充一:VPC Endpoint —— 楼里开的「内部直通小窗」
 (不出大门,就能拿到 AWS 自家服务:S3 / DynamoDB / Secrets Manager 等)
═══════════════════════════════════════════════════════════════════════════

  要解决的问题:
    楼里的私网机器(RDS/Lambda)想访问 AWS 的 S3(对象存储)。
    按老办法,得这样绕一大圈 ↓↓↓

      [厕所 10.0.1.20] → 传达室NAT → 大门IGW → 上城市马路(公网)
                                                    → 再拐回 AWS 的 S3
      缺点:① 慢  ② 走 NAT 要花流量费  ③ 流量暴露到公网,不安全

  解决办法:AWS 在你楼里直接开一扇「内部直通小窗」,楼内取货,不用出门。

    ┌──────────────── VPC 这栋楼 ────────────────┐
    │                                            │
    │   [厕所] RDS 10.0.1.20                      │
    │      │  "我要访问 S3"                        │
    │      ▼                                      │
    │   ┌─────────────────────────────┐          │
    │   │  内部直通小窗                 │          │
    │   │  VPC Endpoint                │          │
    │   │  (楼内私有IP 10.0.1.99)      │──────────┼──► 直连 AWS 的 S3
    │   │                             │          │    (走 AWS 内部网络,
    │   │  域名被解析到这个私有IP,      │          │     根本不碰公网)
    │   │  流量压根不出 VPC             │          │
    │   └─────────────────────────────┘          │
    │                                            │
    └────────────────────────────────────────────┘

  两种小窗:
    ┌──────────────────┬────────────────────────────────────────────┐
    │ Interface Endpoint│ 在你子网里塞一张网卡(ENI)+私有IP。           │
    │ (接口端点)        │ 你就是「你之前问的 VPC interface」!          │
    │                  │ 访问服务域名 → 解析到这个私有IP → 流量不出楼 │
    │                  │ 底层技术叫 PrivateLink,支持大多数AWS服务    │
    ├──────────────────┼────────────────────────────────────────────┤
    │ Gateway Endpoint │ 只服务 S3 和 DynamoDB。                      │
    │ (网关端点)        │ 做法是往路标(RouteTable)里加一条特殊路标,     │
    │                  │ 把去S3的流量直接引走,不走公网               │
    └──────────────────┴────────────────────────────────────────────┘

  一句话:VPC Endpoint = 楼里的内部直通小窗。省钱、更快、更安全,
         私网机器不用出门(NAT/IGW)就能拿到 AWS 自家服务。

 补充二:Transit Gateway (TGW) —— 小区的「中央交通枢纽」
 (连接一堆楼[多个VPC] + 公司自己的机房[本地数据中心])
═══════════════════════════════════════════════════════════════════════════

  要解决的问题:
    你有很多栋楼(VPC-A / VPC-B / VPC-C ...),还有公司自己的机房。
    它们想两两互通。

    老办法 VPC Peering(一对一打洞):
        楼多了就是噩梦 —— 4栋楼要拉6条线,10栋楼要拉45条线!

        A ─── B          A ─── B
        │  ╳  │    →     每两栋楼之间都要单独一条线
        C ─── D          线的数量爆炸 (网状 mesh)

  解决办法:建一个「中央交通枢纽」,每栋楼只拉一条线接过去。

                       ┌─────────────────────┐
          VPC-A ───────┤                     ├─────── VPC-B
                       │  Transit Gateway    │
                       │  中央交通枢纽 TGW    │
          VPC-C ───────┤  (总调度中心)        ├─────── VPC-D
                       │                     │
                       └──────────┬──────────┘
                                  │
                                  │ 还能接
                                  ▼
                        公司自己的机房(本地数据中心)
                        (通过 VPN 或专线 Direct Connect)

        星状(star):每栋楼只需 1 条线 → 中心统一转接
        新增一栋楼?接一条线到枢纽就行,不用改其他所有楼。

  怎么用(对应代码):
    每栋楼的路标里加一条,把「去别的楼」的流量指向枢纽:

        // VPC_rules.ts 里 Route 早就预留了 tgw:
        interface Route {
          target: string;  // "local"|"igw-xxx"|"nat-xxx"|"tgw-xxx"
        }                   //                            └── 就是它!

        privateRT.addRoute("10.1.0.0/16", tgw);  // 去B楼 → 走枢纽
        privateRT.addRoute("10.2.0.0/16", tgw);  // 去C楼 → 走枢纽

  一句话:Transit Gateway = 小区中央交通枢纽。
         把"每两栋楼互相拉线(网状)"简化成"每栋楼接一条线到中心(星状)",
         还能顺便把公司本地机房也接进这张大网。

 补充三:VPC Peering —— 两栋楼之间「私挖的地下通道」
═══════════════════════════════════════════════════════════════════════════

  要解决的问题:
    我就两三栋楼(VPC),想让它们互通,又觉得建"中央枢纽TGW"太重了。

  解决办法:在两栋楼之间直接挖一条一对一的专用地下通道。

        ┌─────────────┐                    ┌─────────────┐
        │   VPC-A     │ ══════通道═════════ │   VPC-B     │
        │ 10.0.0.0/16 │   (Peering 直连)    │ 10.1.0.0/16 │
        └─────────────┘                    └─────────────┘

    对应代码:两边路标各加一条,指向对方
        vpcA_RT.addRoute("10.1.0.0/16", pcx);  // 去B楼 → 走通道
        vpcB_RT.addRoute("10.0.0.0/16", pcx);  // 去A楼 → 走通道

  ★ 两个致命限制(所以楼一多就崩):
    ① 不能「借道」(no transitive routing):
         A 挖了通道到 B,B 挖了通道到 C,
         但 A 想找 C 是不行的! 必须 A 自己再单独挖一条到 C。
         ┌───┐   ┌───┐   ┌───┐
         │ A │───│ B │───│ C │    A 到 C? ❌ 走不通!
         └───┘   └───┘   └───┘    B 不会帮 A 转发给 C
    ② 楼一多,通道数量爆炸(网状 mesh):
         这正是【中央枢纽 Transit Gateway】要取代它的原因。
         ┌────────────┬──────────────────────────────────┐
         │ 少数几栋楼  │ 用 Peering(简单、便宜、延迟低)      │
         │ 很多栋楼    │ 用 Transit Gateway(星状、可扩展)   │
         └────────────┴──────────────────────────────────┘

  一句话:VPC Peering = 两栋楼私挖的一对一地下通道。
         简单直连,但不能借道、楼多了要拉爆炸数量的线。

 补充四:VPN / Direct Connect —— 把「公司自己的机房」接进 AWS
═══════════════════════════════════════════════════════════════════════════

  要解决的问题:
    公司在自己办公室/机房有一批老服务器(本地数据中心),
    想让它们和 AWS 里的楼(VPC)互通,像在同一个内网里。

  两种接法:

    ① VPN —— 在公网上挖的「加密隧道」
       ┌──────────────┐                            ┌──────────────┐
       │ 公司自己机房   │ ~~~~加密隧道~~~~ 公网 ~~~~~ │  AWS VPC     │
       │ (本地数据中心) │   (数据加密,别人看不懂)      │              │
       └──────────────┘                            └──────────────┘
       比喻:在公共马路上开一辆装了防偷窥玻璃的车。走的还是公共路,
             但车里内容外人看不见。
       特点:便宜、几分钟就能建、但走公网 → 延迟/稳定性看运气。

    ② Direct Connect (DX) —— 花钱拉的「专用物理光纤」
       ┌──────────────┐                            ┌──────────────┐
       │ 公司自己机房   │ ══专属光纤(不走公网)═════════│  AWS VPC     │
       └──────────────┘                            └──────────────┘
       比喻:出钱给你家和公司之间修了一条私人专用隧道,
             不跟任何人共享马路。
       特点:贵、上线要数周、但稳定、低延迟、私密,适合生产/大流量。

    ┌────────────────┬──────────────┬────────────────────┐
    │                │ VPN          │ Direct Connect     │
    ├────────────────┼──────────────┼────────────────────┤
    │ 走哪            │ 公网(加密)   │ 专用物理线路        │
    │ 价格            │ 便宜         │ 贵                 │
    │ 上线速度        │ 几分钟       │ 几周(要拉线)       │
    │ 稳定/延迟       │ 看公网脸色   │ 稳定、低延迟        │
    │ 典型用途        │ 临时/小流量  │ 生产/大流量/合规    │
    └────────────────┴──────────────┴────────────────────┘

    (这两者都常常再接到【中央枢纽 Transit Gateway】上,统一进大网)

  一句话:VPN = 公网上的加密隧道(便宜快但看公网脸色);
         Direct Connect = 专用物理光纤(贵但稳)。
         都是把公司自己的机房接进 AWS 的手段。

 补充五:NACL —— 「楼层大门的保安」,和房间门口的保安(安全组)是两道岗
═══════════════════════════════════════════════════════════════════════════

  楼里其实有【两层保安】,你的包要过两道岗才能到机器:

        城市马路
           │
           ▼
    ┌──────────────────────────────────────┐
    │  楼层大门保安 = NACL                   │  ← 第一道岗(子网级别)
    │  管整层楼的进出                        │
    └──────────────┬───────────────────────┘
                   ▼
    ┌──────────────────────────────────────┐
    │  房间门口保安 = Security Group          │  ← 第二道岗(机器级别)
    │  只管这一个房间(这台机器)              │
    └──────────────┬───────────────────────┘
                   ▼
              机器 (ENI)

  两者最关键的区别 —— 「有没有记忆」:

    ┌──────────────┬───────────────────────┬──────────────────────────┐
    │              │ 安全组 SecurityGroup  │ NACL                     │
    ├──────────────┼───────────────────────┼──────────────────────────┤
    │ 管哪一级      │ 单台机器(ENI)        │ 整个子网(楼层)           │
    │              │                       │                          │
    │ 有无记忆      │ ★有状态(有记忆)      │ ★无状态(没记忆)          │
    │ (关键!)      │ 放你进来,就自动记得   │ 进、出要分别单独放行!     │
    │              │ 放你的回话出去        │ 放行进来 ≠ 放行出去       │
    │              │                       │                          │
    │ 规则类型      │ 只能白名单(允许)     │ 允许 + 拒绝都行           │
    │              │ 不能写"拒绝某IP"      │ 能写"拉黑某IP"(黑名单)    │
    │              │                       │                          │
    │ 规则怎么判    │ 所有规则综合看        │ 按编号从小到大,          │
    │              │                       │ 命中第一条就停           │
    │ 默认          │ 入站全拒/出站全放     │ 默认全放行(需自己收紧)   │
    └──────────────┴───────────────────────┴──────────────────────────┘

  「有无记忆」举例(这是最容易踩坑的点):
    你从外面访问机器的 443 端口:
      · 安全组:你放行了"入站443",回话自动能出去 ✓ (它记得你)
      · NACL:  你放行了"入站443",但【回话走的是随机高端口】,
               如果你没另外放行"出站 1024-65535",回话就被卡住!
               因为 NACL 没记忆,不知道这个出去的包是刚才那个请求的回话。

  实践建议:
    · 绝大多数情况:只用【安全组】就够了(有状态,好用不易错)。
    · NACL 通常保持默认全放行,只在需要「整层楼级别拉黑某些IP」
      或「多一道兜底防线」时才动它。

  一句话:NACL = 楼层大门保安(子网级、无记忆、能拉黑名单);
         安全组 = 房间门口保安(机器级、有记忆、只白名单)。
         日常用安全组,NACL 当兜底。

    技术名词            楼里的比喻              一句话
    ───────────────    ──────────────────    ────────────────────────

 补充六:站在「楼外面」的边缘服务 + 分层防火墙全景

  关键认知:

    │                                                          │
    │  比喻:你总部在悉尼(你的VPC那栋楼),但你在东京、伦敦、     │

    │  │                                                │      │

    │  层级          服务              管什么              比喻          │
    │  ───────────  ───────────────  ─────────────────  ─────────────  │

 补充七:子网掩码 / CIDR (/16 /24 到底是啥) —— 楼怎么分层的地基
═══════════════════════════════════════════════════════════════════════════

  这个概念一直在代码和图里出现,但没专门讲过:
    VPC   用 10.0.0.0/16   ← 那个 /16 是啥?
    Subnet 用 10.0.1.0/24  ← 那个 /24 又是啥?
    这后面的 /数字 就是「子网掩码」的简写(叫 CIDR 写法)。


  ★ 核心:子网掩码 = 一把「分界尺」,把 IP 切成两半 ★

    一个 IP 地址(如 10.0.1.20)在电脑眼里是 32 个二进制位(4段×8位):
        10  .   0   .   1   .  20
      00001010.00000000.00000001.00010100
      └──────────────────┘└────────┘
         网络号(哪栋楼)      主机号(哪个房间)

    子网掩码这把尺子,决定「从第几位切开」:
      · 尺子前面画斜线的部分 = 网络号 = "哪栋楼/哪层楼"(大家共用,固定)
      · 尺子后面剩下的部分   = 主机号 = "具体哪个房间"(可以变化)


  ★ /数字 = 前面有多少位是「网络号」(楼号那部分) ★

    ┌──────────────┬─────────────┬──────────────┬─────────────────┐
    │ 写法          │ 网络位(固定) │ 主机位(可变) │ 能装多少房间     │
    ├──────────────┼─────────────┼──────────────┼─────────────────┤
    │ 10.0.0.0/16  │ 前16位固定   │ 后16位可变   │ ~65536 (整栋楼) │
    │ 10.0.1.0/24  │ 前24位固定   │ 后8位可变    │ 256   (一层楼)  │
    │ 10.0.1.0/28  │ 前28位固定   │ 后4位可变    │ 16    (一个套间)│
    │ x.x.x.x/32   │ 全32位固定   │ 0位可变      │ 1 (就指某一台机)│
    └──────────────┴─────────────┴──────────────┴─────────────────┘

    规律:/数字 越大 → 固定的位越多 → 留给房间的位越少 → 网段越小
          /16 是大楼,  /24 是一层,  /28 是套间,  /32 精确到一个房间

    (还记得吗?给安全组放行你的IP时写 "123.45.67.89/32",
     那个 /32 就是"只精确指这一台机器",一个房间都不多放。)


  ★ 为什么 VPC 用 /16、Subnet 用 /24 ★

    VPC (整栋楼)   10.0.0.0/16   → 预留一大片地址(6万多个)
       ├ Subnet 一层 10.0.0.0/24  → 从大楼里切出第0层(256个)
       ├ Subnet 一层 10.0.1.0/24  → 切出第1层
       └ Subnet 一层 10.0.2.0/24  → 切出第2层  ...
    大楼(/16)地址够多,可以往里切很多个小的层(/24),互不重叠。
    这就是代码里 Subnet 构造函数要检查的两件事:
       ① 必须在 VPC 范围内   (子网这把小尺子要落在大楼地址段里)
       ② 不能和已有子网重叠  (两层楼不能抢同一批房间号)


  ★ 掩码怎么判断"两个IP在不在同一网段"(即代码 IPRange.contains) ★

    做法:拿掩码把两个IP的"网络号部分"抠出来比一比,相同就在同一段。

    例:10.0.1.0/24 里,前24位(10.0.1)是网络号
        10.0.1.20 的前24位 = 10.0.1  ┐
        10.0.1.99 的前24位 = 10.0.1  ┘ 相同 → 在同一子网 ✓(走廊直达)
        10.0.2.5  的前24位 = 10.0.2    不同 → 不在  ✗(得走路由)

    这正是 VPC_rules.ts 里这两个方法在干的事:
        contains(ip)      → 这个IP的网络号 落在我的范围里吗?
        overlaps(other)   → 两个范围的网络号 有没有交叉?
    (代码里方法体是空的注释,原理就是上面这套"抠网络号来比")


  ★ 顺便:为什么子网可用IP要减5个 (代码里的 slice(4,-1)) ★

    一个 /24 有256个地址,但不是256个都能给机器用,AWS 每个子网保留5个:
        .0   网络地址本身(代表"这层楼"这个整体)
        .1   VPC 路由器占用
        .2   AWS DNS 占用
        .3   AWS 预留(future)
        .255 广播地址(代表"喊这层楼所有人")
    所以 256 - 5 = 251 个才是真正能分给机器的。
    → 这就是代码 availableIPs = generateIPs(cidr).slice(4, -1) 的由来
      (砍掉前4个 + 最后1个)


  一句话:子网掩码(/16 /24) = 一把分界尺,决定IP里"哪几位是楼号、
         哪几位是房间号"。数字越大网段越小。VPC是大楼(/16),
         Subnet是楼层(/24),/32则精确到某一台机器。

 补充九:负载均衡器 Load Balancer (ELB 家族) —— 大堂的「分流引导员」
 ★ 考证高频! 核心记法:按"工作在网络第几层"来分 ★
═══════════════════════════════════════════════════════════════════════════

  分流员要解决的问题:
    你后端有好几台机器扛流量,总不能让用户全挤到第1台(累死)、
    其他几台闲着。分流员站大堂,把客流均匀分给每台机器。
    好处:① 不让单台过载 ② 一台挂了自动把流量转给活着的(高可用)


  ★ 先补个地基:网络分层(OSI,考试常考,记住这几层就够)★

    第7层 应用层   看得懂 HTTP:URL、域名、Cookie、请求头
    第4层 传输层   只认 TCP/UDP + IP和端口,不拆开看内容
    第3层 网络层   只认 IP 包本身
    → AWS 的三种分流员,就是分别站在这三层干活的。


  ★ 三种分流员 (Classic 已淘汰,考试基本不考,忽略) ★

  ┌──────────────────────────────────────────────────────────────────┐
  │ ① ALB  Application Load Balancer  —— 第7层(应用层)               │
  │   A = Application = 看得懂内容                                     │
  │                                                                   │
  │   能看懂 HTTP:URL路径 / 域名 / 请求头 / Cookie                    │
  │   → 能做「智能分流」(按内容路由):                                 │
  │       /api/*    → 后端A组                                         │
  │       /images/* → 后端B组                                         │
  │       手机来的  → 后端C组                                         │
  │                                                                   │
  │   比喻:能看懂你要办啥业务的引导员                                 │
  │        "办信用卡去3号窗,取款去5号窗"                              │
  │   用途:网站、API、微服务 —— 绝大多数 Web 场景默认选它            │
  └──────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────────┐
  │ ② NLB  Network Load Balancer  —— 第4层(传输层)                   │
  │   N = Network = 只看IP和端口,不拆内容                             │
  │                                                                   │
  │   极快、能扛超高并发、超低延迟、可给固定IP(静态IP/EIP)            │
  │   看不懂 HTTP 内容(它不拆包,所以快)                              │
  │                                                                   │
  │   比喻:不问你办啥、只按窗口号机械分流的引导员,速度飞快           │
  │   用途:超高性能、游戏、金融交易、IoT、需要固定IP的场景            │
  └──────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────────┐
  │ ③ GWLB  Gateway Load Balancer  —— 第3层(网络层)                  │
  │   GW = Gateway = 把流量牵去"安检"                                 │
  │                                                                   │
  │   特殊用途:把流量先导到第三方安全设备(防火墙/入侵检测IDS/IPS)    │
  │   过一遍安检,再放行到后端                                        │
  │                                                                   │
  │   比喻:把所有客人先领去安检门过一遍的引导员                       │
  │   用途:给流量串接第三方防火墙/安检设备(安全合规场景)            │
  └──────────────────────────────────────────────────────────────────┘


  ★ 一张表背下来(考试速记)★

    ┌────────┬────────┬──────────────┬────────────────┬──────────────┐
    │ 类型    │ 层     │ 看什么        │ 特点           │ 典型用途     │
    ├────────┼────────┼──────────────┼────────────────┼──────────────┤

    ├────────┼────────┼──────────────┼────────────────┼──────────────┤
    │ GWLB   │ 3网络层│ IP包          │ 串接第三方安检 │ 防火墙/IDS/IPS│

    一句话记法:
      A(pplication)=7层=看内容=智能分流(网站首选)
      N(etwork)   =4层=看IP端口=极快(高性能/固定IP)
      G(ateway)   =3层=牵去安检(串第三方防火墙)


  ★ 几个考试爱考的关联知识点 ★

    · 健康检查(Health Check):
        分流员会定时"点名"每台后端机器还活着吗?
        挂了的自动踢出,不再往它发流量 → 这就是"高可用"的来源。

    · Target Group(目标组):
        分流员不直接连机器,而是连一个"目标组"(一堆机器的集合)。
        ALB 可按规则把不同请求发给不同目标组。

    · 跨可用区(Multi-AZ):
        分流员能把流量分到不同机房(AZ)的机器,
        一个机房整个挂了,另一个机房照常服务 → 容灾。

    · 和前面服务的配合(完整链路):
        用户 → Route53(DNS) → CloudFront(CDN,带WAF/Shield)
             → ALB/NLB(分流员) → 后端机器(过NACL/安全组)
        分流员通常放在 Public 子网,后端机器放在 Private 子网。


  一句话:负载均衡器 = 大堂分流引导员,把流量均分给多台机器并踢掉挂掉的。
         AWS 三种按"工作在第几层"分:
         ALB(7层看内容/最常用)、NLB(4层看IP端口/最快)、GWLB(3层牵去安检)。
